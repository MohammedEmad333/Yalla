# 05 — الدفع والمحفظة

آخر مراجعة: 2026-10-05

> هذا الملف كان يوثّق تصميمًا أقدم لشحن المحفظة اليدوي عبر عدة مزودين. تدفق طلبات المتاجر الحالي يعتمد **Jawwal Pay** للدفع المباشر، لذلك لا تعتبر قائمة Bank of Palestine/PalPay أو `services/payment/` القديمة وصفًا للحالة الحالية.

## الدفع الحالي للطلب

عند إنشاء طلب مطعم/متجر من API التجارة:

1. الخادم يتحقق من المتجر، الأصناف، الأسعار، الخيارات، المخزون والخصومات.
2. الطلب يُنشأ بحالة انتظار الدفع عندما يكون الدفع مطلوبًا.
3. `directPayment.service.js` يبدأ جلسة Jawwal Pay.
4. رقم محفظة جوال يُطبّع ويتحقق منه بصيغة الهاتف الفلسطيني المدعومة.
5. الخادم يطلب عملية دفع من `jawwalPayClient.js` بمفتاح idempotency مرتبط بالطلب.
6. بعد إرسال OTP تصبح عملية الدفع بحالة `otp_sent`.
7. تأكيد OTP الناجح يعلّم `OrderPayment` كـ`paid` ويستدعي تفعيل الطلب المدفوع.
8. عند الفشل/الإلغاء، لا يجب تفعيل الطلب؛ وتُحرر الحجوزات المرتبطة مثل المخزون/النقاط حسب المسار.

المزوّد الحالي المسجل لدفعات الطلب:

```text
jawwal_pay
```

## ملفات التنفيذ الأساسية

```text
backend/src/services/directPayment.service.js
backend/src/services/jawwalPayClient.js
backend/src/services/jawwalRefund.service.js
backend/src/models/OrderPayment.js
backend/src/routes/commerce.routes.js
backend/src/routes/jawwalRefund.routes.js
```

راجع الكود الفعلي قبل توثيق endpoint جديد أو حالة دفع إضافية.

## إنشاء طلب مدفوع

`commerce.routes.js` يفرض المصادقة كمستخدم ويطبق middleware الصيانة قبل إنشاء الطلب. إنشاء الطلب وإعادة الطلب يستخدمان `{ paymentRequired: true }` ثم يبدأان Jawwal Pay مباشرة.

إذا تعذر إنشاء جلسة الدفع بعد إنشاء الطلب، يحاول الخادم إلغاء مسار الدفع/الطلب بدل ترك طلب نشط بدون دفعة سليمة.

## Idempotency

الدفع يستخدم مفتاحًا مشتقًا من `orderId`، ما يمنع إنشاء دفعات مستقلة مكررة لنفس الطلب عند إعادة المحاولة. كذلك إنشاء الطلب يدعم `Idempotency-Key` على مستوى API.

لا تغيّر قواعد idempotency دون اختبارات لأن التكرار هنا مالي.

## حالات مهمة

الحالات الدقيقة يجب أخذها من models/services، لكن التدفق المباشر يتعامل على الأقل مع:

```text
created / otp_sent / paid / cancelled / refunded
```

لا تعتبر نجاح استدعاء HTTP وحده إثبات دفع؛ حالة المزود والتحقق النهائي هما مصدر القرار.

## تأكيد الدفع

OTP يجب أن يمر عبر backend، ولا يجب تسجيله في logs أو analytics. بعد تأكيد المزود:

- تُحدّث عملية الدفع إلى `paid`.
- يُحفظ المرجع/transaction ID المتاح من المزود.
- يُفعّل الطلب المدفوع بشكل idempotent.

إذا كان الدفع مسجلًا كمدفوع أصلًا، إعادة التأكيد يجب ألا تخصم المبلغ مرة ثانية.

## فحص حالة الدفع

الخدمة تستطيع إعادة قراءة العملية المحلية والاستعلام من Jawwal Pay عند الحاجة. هذا مهم عند انقطاع الاتصال بعد الدفع وقبل وصول استجابة العميل.

## الإلغاء والاسترداد

- الدفعة غير المكتملة يمكن إلغاؤها عبر المسار المدعوم.
- الدفعات المكتملة لا تُلغى كأنها لم تحدث؛ استخدم منطق refund المخصص.
- `jawwalRefund.service.js` هو المرجع الحالي للاستردادات المرتبطة بجوال.

أي استرداد مالي يجب أن يكون idempotent ومدققًا وألا يعتمد على حالة UI فقط.

## المحفظة الداخلية

المشروع ما زال يحتوي خدمات محافظ للمستخدم/الكابتن/الإدارة لأغراض الرصيد والتسويات. **لا تخلط بين المحفظة الداخلية وبين دفع Jawwal Pay للطلب.** إذا تغيرت سياسة شحن الرصيد أو أعيد تفعيل top-up، وثّقها من implementation الحالي بدل إعادة استخدام التصميم التاريخي متعدد المزودين.

## الأمان

- لا تضع credentials الخاصة بـJawwal Pay في المستودع أو Markdown.
- لا تسجل OTP أو access tokens أو payloads حساسة.
- استخدم HTTPS فقط في الإنتاج.
- طبّع رقم الهاتف في الخادم ولا تثق بقيمة العميل الخام.
- حافظ على idempotency للإنشاء والتأكيد والاسترداد.
- لا تجعل العميل يقرر أن الطلب مدفوع؛ القرار من backend بعد تأكيد المزود.

## الاختبار قبل النشر

تحقق من السيناريوهات التالية على بيئة آمنة/مزود الاختبار إن توفر:

- إنشاء جلسة دفع.
- OTP صحيح وخاطئ.
- إعادة محاولة تأكيد نفس الدفع.
- انقطاع العميل ثم استعلام الحالة.
- إلغاء قبل الدفع.
- عدم تفعيل الطلب عند فشل إنشاء جلسة الدفع.
- استرداد دفعة مكتملة وفق الصلاحيات.
